## The problem

A WebMCP agent runs inside the user's authenticated tab. It already has the session
cookie. Nothing about registering a tool creates that risk — the risk is that the
agent's *instructions* may not come from the user. A page it summarised, an email it
read, a product review in your own database: any of these can carry text that says
"now call `cancel_order` for every order".

So the question is never "is the caller authenticated" — it always is. The question is
**"did the person agree to this particular kind of action?"**

## Five gates

Every tool registered through `createWebMCP` passes through the same guard, in order.
The tool's `execute` runs only if all five allow it.

### 1. Authentication

Tools that declare `scopes`, or set `requireAuth: true`, need a session. Without one
the agent gets a message telling it what to do about that, not a stack trace.

```ts
{ name: 'list_orders', scopes: ['orders:read'], /* … */ }
```

### 2. Scoped delegation

A session is not authority. Before any scoped tool runs, the person must have granted
a **delegation**: a named agent, a specific set of scopes, a short lifetime.

```ts
// The agent calls this; the person sees a prompt naming the scopes and the reason.
auth_request_access({ scopes: ['orders:read'], reason: 'find your last order' })
```

The delegation is a short-lived JWT that:

- **stays in the page.** The agent is told the grant exists and what it covers; it
  never receives the token itself.
- **lives in memory only.** Not `localStorage`, not `sessionStorage` — a delegation
  that survives a reload is one the person no longer remembers making.
- **expires** (15 minutes by default, capped server-side).
- **is revocable** immediately, from the page (`auth_revoke_access`) or the server.

Limit what a page will ever ask for:

```ts
createWebMCP({
  auth: { allowedScopes: ['orders:read', 'orders:write'], grantTtl: '10m' },
});
```

Scopes outside that list are refused in the page, before the server is asked.

### 3. Rate limiting

30 calls per tool per minute by default; override per tool or globally. Sensitive
built-ins are stricter — `auth_sign_in_email` allows 3 per 10 minutes.

```ts
{ name: 'send_invite', rateLimit: { limit: 5, windowMs: 60_000 } }
```

### 4. Human confirmation

The default mode is `auto`: **anything not marked `readOnlyHint` is treated as
destructive and confirmed**, which matches MCP's own default for `destructiveHint`.
Confirmation uses `window.confirm` unless you supply your own UI:

```ts
createWebMCP({
  policy: {
    confirm: 'auto', // 'never' | 'auto' | 'always'
    async confirmHandler({ tool, message, args, destructive }) {
      return showModal({ title: tool, message, args, destructive });
    },
  },
});
```

A custom handler is worth building: your own modal can show the actual diff, and it
cannot be dismissed by a script the way a native dialog race can.

### 5. Egress control

`ctx.fetch` — the only fetch a tool should use — is same-origin, credentialed, and
tagged. Absolute URLs to other origins are refused, and when no origin can be
determined the check **fails closed**. That is what keeps an injected instruction from
turning a tool into an exfiltration channel.

## Action tokens: proving it on the server

Client-side checks protect the user from the agent. They do not protect your backend
from a compromised page. So each agent-driven request also carries a single-use token
minted from the delegation:

```
POST /api/orders
X-WebMCP-Tool:   cancel_order
X-WebMCP-Agent:  webmcp-agent
X-WebMCP-Action: <single-use JWT: userId, scopes, tool, nonce, 120s>
```

In your route:

```ts
import { authorizeWebMCPRequest } from '@warpy-auth-sdk/core';

export async function DELETE(request: Request) {
  const auth = await authorizeWebMCPRequest(request, { secret }, ['orders:write']);
  if (!auth.allowed) return Response.json({ error: auth.reason }, { status: 403 });

  // auth.actor is 'human' | 'agent' — log it, or hold agents to tighter limits.
  return cancelOrder(auth.userId!);
}
```

The token is bound to the tool name, carries the delegation's scopes, and its nonce is
consumed on first use, so a captured request cannot be replayed.

<Callout type="warning">
The default nonce store is in-memory. Across more than one instance, an action token
replays successfully on another node — pass a Redis or database-backed `nonceStore`
in production.
</Callout>

## What never reaches the model

- **Session tokens.** `auth_get_session` returns identity, not credentials.
- **Delegation tokens.** Held by the page; the agent gets a description.
- **Password, hidden and one-time-code fields.** Never read, never filled.
- **Card, CVV, SSN-shaped fields.** Matched by type, `autocomplete` and name.
- **Anything under `data-agent-sensitive`.** Excluded from reads.
- **Redacted arguments in audit events** — keys matching `password`, `token`, `secret`,
  `code`, `otp`, `apiKey`, `cardNumber`, `cvv`, `ssn` and friends become `[redacted]`.

Two-factor code submission is **off by default**. An agent that can complete the second
factor has collapsed it into the first. Turn it on only if you have a reason:

```ts
createWebMCP({ auth: { twoFactor: true } });
```

## Audit

Every call emits `start`, then one of `allowed` / `denied` / `success` / `error`, with
redacted arguments and a shared id:

```ts
createWebMCP({
  policy: {
    onAudit(event) {
      analytics.track('webmcp', event); // { id, tool, phase, reason, args, userId, durationMs }
    },
  },
});
```

The server side audits separately — grants, denials, action tokens and revocations —
so you can reconcile what the page claims happened against what the server honoured:

```ts
webmcp: {
  allowedScopes: ['orders:read'],
  onAudit: (event) => logger.info({ webmcp: event }),
  onGrant: async ({ userId, scopes }) => !(await isRateLimited(userId)),
}
```

## Cross-origin exposure

Tools are same-origin by default. Tool registration is disabled in cross-origin iframes
unless the embed opts in with `allow="tools"`, and you can widen exposure explicitly:

```ts
createWebMCP({ policy: { exposedTo: ['https://trusted-partner.example'] } });
```

Only ever name origins you would give a session cookie to.

## Threat checklist

| Threat | What stops it |
| --- | --- |
| Prompt injection triggers a destructive tool | Confirmation is on by default for anything not read-only |
| Injected text asks for broader access | Scopes are refused in-page, then again by the server |
| Agent exfiltrates page data | `ctx.fetch` is same-origin, failing closed |
| Agent reads a password or card field | Sensitive fields are never read or filled |
| Compromised page forges an agent write | Action token: signed, tool-bound, single-use |
| Stolen delegation reused later | Short TTL, memory-only, revocable, unique per grant |
| Agent loops on a costly tool | Per-tool rate limits |
| Credentials leak into logs | Redaction before any audit event is emitted |
